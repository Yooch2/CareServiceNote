# 평가 결과 모음

가상 시나리오로 분류·요약·알림 품질을 잰 기록입니다. 실제 인물·기록은 없습니다.
평가셋은 `backend/app/evaluation/dataset.py`, 실행은 `uv run python -m app.evaluation --help`.

## 진행 순서

1. **dev 시나리오 14개**로 지금 프롬프트를 쟀다 → `1-before-dev-*.md`
2. 문제를 보고 고치기 전에 **holdout 시나리오 5개**를 새로 만들어 같은 프롬프트로 먼저 쟀다 → `1-before-holdout-*.md`
3. **dev에서 본 문제만 보고** 프롬프트 세 줄과 후처리 하나를 고쳤다
4. dev와 holdout을 다시 쟀다 → `2-after-*.md`

holdout은 고칠 때 보지 않은 시나리오라서, holdout 숫자가 같이 좋아지면 평가셋에만 맞춘 개선이 아니라고 볼 수 있습니다(5개라 근거로는 약합니다).

## 고친 것

| 문제 (dev에서 발견) | 고친 곳 |
|---|---|
| "무릎 담요를 덮어 드림"에 무릎 불편 부위를 붙임 | 프롬프트: 불편·통증을 말할 때만 부위, 그 부위에 쓰는 물건·돌봄 동작은 null |

| 로컬 모델이 여러 주제를 한 항목으로 합침 | 프롬프트: 주제가 다른 말은 한 문장 안에 있어도 나눔 |
| 로컬 모델이 답 없는 이전 확인 사항에 결과 "null"을 적음 | 후처리: 근거가 전사문에 없는 후속 확인 답은 버림 (요양보호사가 직접 쓸 수 있게 미입력으로 남음) |

## 해석

- **서버 쪽 확인은 두 모델 모두에 효과가 있었다.** 근거 없는 후속 확인 답 버리기로 로컬 모델의 지어낸 답이 3 → 0이 됐다. 근거 대조(1단계부터), 요약 근거 검증(2단계)도 두 모델 모두 100%를 유지했다.
- **프롬프트 개선은 Gemini에는 효과가 있었고, 7B 로컬 모델에는 엇갈렸다.** Gemini는 dev와 holdout이 함께 올랐다. 로컬 모델은 지어낸 기분이 줄었지만 항목을 더 많이 합쳐서 재현율과 위험 표시 재현율이 떨어졌다. 규칙이 길어지면 작은 모델은 "나눠 적으라"는 규칙을 오히려 덜 지켰다.
- **무릎 담요 부위 오탐은 두 모델 모두 완전히 없애지 못했다.** 부위 오탐은 알림 규칙으로 이어질 수 있지만, 요양보호사가 검토 화면에서 확인해야 확정되고, 알림은 서로 다른 두 방문이 필요해서 한 번의 오탐으로 알림이 생기지는 않는다.
- **로컬 모델이 같은 항목을 끝없이 반복하는 경우**(h-handwash)를 찾았다. `"content": "null"` 항목을 계속 만들다 매번 2분 HTTP 시간 초과로 끝났고, 워커는 이를 일시 오류로 보고 세 번 다시 시도했다. 출력 길이 한도(`num_predict`)를 두고 한도에 닿으면 재시도 없이 `llm_output_too_long`으로 실패시켜 직접 작성으로 넘기게 했다.
  - 처음에는 한도를 2048토큰으로 잡았는데 다시 재 보니 여전히 시간 초과였다. 보통 출력이 260~360토큰, 이 맥에서 초당 약 12토큰이라 2048토큰은 약 170초로 120초 시간 초과보다 길었다. 1024토큰(약 85초)으로 낮춘 뒤 이 시나리오는 82초 만에 `llm_output_too_long`으로 끝난다(이전: 120초 × 3회).
- 데모(배포)는 Gemini를, 비용 0원 로컬 실행은 qwen2.5:7b를 쓰는 지금 구성이 맞다고 본다. 로컬 모델 품질은 더 큰 모델이나 예시를 넣은 프롬프트로 나중에 다시 재 볼 수 있다.

## 한계

- 시나리오가 dev 14개, holdout 5개로 적다. 숫자 하나하나보다 경향과 틀린 사례 목록을 보는 용도다.
- 정답은 제가 정했다. 말씀/관찰 경계처럼 사람마다 다르게 볼 수 있는 경우가 있다(예: "어깨가 결려서 팔을 올리기 힘들다고 하셨음"을 관찰로 분류).
- 전사 평가는 macOS `say`의 깨끗한 합성 음성이라 실제 현장 음성(소음, 사투리)보다 훨씬 쉽다.
- Gemini는 무료 등급 한도 때문에 1~2회만 반복했다.
