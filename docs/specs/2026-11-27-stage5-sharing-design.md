# 5단계 설계: 보호자 하루 요약 · 방문 시작/종료 · 우려 처리 결과 공유 · 업무 메시지

작성일 2026-11-27

## 1. 목표와 범위

기획안의 "보호자 하루 요약은 수급자 동의 범위 안에서 작성하고 담당자 승인 후 공유"와, 3단계에서 정한 5단계 범위(방문 체크인·아웃 알림, 우려와 처리 결과의 보호자 공유, 업무 메시지)를 만든다.

포함
- **보호자 하루 요약**: 확정된 방문 하나에 대해 AI가 보호자용 짧은 요약(최대 3문장)을 쓴다. 문장마다 근거 항목을 단다. 기관 담당자가 읽고 고치거나 문장을 지운 뒤 **승인**해야 보호자에게 보인다.
- **열람 범위 적용**: 요약은 방문당 하나만 만들고, 보호자에게 보낼 때 문장의 근거 항목이 모두 그 보호자의 열람 범위 안에 있는 문장만 남긴다.
- **방문 시작·종료**: 요양보호사가 수급자 화면에서 "방문 시작", "방문 종료"를 누른다. 보호자 화면에 오늘 방문 시각이 나온다. 위치는 수집하지 않는다.
- **우려 처리 결과 공유**: 기관 담당자가 알림을 처리할 때 보호자에게 보낼 안내문을 따로 쓰면 보호자 화면의 "센터 안내"에 나온다. 알림 원문(근거, 요양보호사가 쓴 우려)은 보내지 않는다.
- **업무 메시지**: 수급자별로 기관 담당자와 담당 요양보호사가 주고받는 짧은 메시지(방문 일정 변경, 준비물 등). 보호자는 볼 수 없다.

제외
- 푸시·문자 알림 (앱 안에서만)
- 보호자 → 센터 문의 (보호자는 계속 읽기 전용)
- 메시지 수정·삭제, 읽음 표시
- 월간 상담 요약 (기획안의 "용도별 조회 기간"은 2단계 인계 요약의 7·14·30일로 갈음)

## 2. 결정과 이유

| 결정 | 이유 |
|---|---|
| 요약은 **방문당 하나**, 보호자별로 **문장 단위로 거름** | 보호자마다 범위가 달라 보호자별로 요약을 만들면 AI 호출과 승인 일이 보호자 수만큼 늘어난다. 2단계 인계 요약처럼 문장마다 근거 항목이 있으니, 범위 밖 항목을 근거로 쓴 문장만 빼면 된다. |
| AI 입력은 **확정 항목만** (전사문 X) | 전사문에는 보호자에게 보이면 안 되는 말이 섞일 수 있다. 확정된 항목만 넣고 이름·UUID 없이 참조 번호만 쓴다(2단계와 같음). |
| **승인 전에는 보호자에게 안 보임**, 승인 취소 가능 | 기획안 그대로. 잘못 승인한 경우를 위해 취소를 둔다. |
| 담당자가 **문장 수정 가능**, 근거는 유지 | 표현을 다듬는 정도는 사람이 책임진다. 근거 항목은 바꿀 수 없게 해서 열람 범위 거르기가 계속 동작한다. 수정한 문장은 `edited` 표시. |
| 요약 만들기는 **기관 담당자만**, 보호자 공유 동의 필요 | 승인할 사람이 만든다. 공유 목적의 처리라 공유 동의가 있어야 한다. |
| AI 호출 한도는 **인계 요약과 같은 하루 한도를 같이 씀** | 무료 등급 보호. `ai_usage`에 종류만 다르게 남기고 합산한다. |
| 방문 시작/종료는 **요양보호사당 열린 방문 하나** | 부분 unique 인덱스. 종료 없이 다른 수급자를 시작하면 409로 먼저 종료하게 한다. |
| 위치 수집 안 함 | 기획 범위 밖이고 민감정보가 늘어난다. 시각만 남긴다. |
| 처리 결과 공유는 **담당자가 쓴 안내문만** | 알림 근거와 요양보호사의 우려 원문에는 다른 기록 내용이 섞인다. 보호자에게 보낼 문장을 사람이 따로 쓴다. |

## 4. API

| API | 누가 | 설명 |
|---|---|---|
| `GET /records/{id}/guardian-summary` | 직원 | 없으면 null |
| `POST /records/{id}/guardian-summary` | 기관 담당자 | AI로 (다시) 만들기. 확정 기록 + 공유 동의 필요, 승인된 요약은 409(먼저 승인 취소) |
| `PUT /records/{id}/guardian-summary` | 기관 담당자 | `{sentences: [{text}]}` 같은 순서로 문장 수정, 빈 문장은 삭제. 문장 추가 불가 |
| `POST /records/{id}/guardian-summary/approve` · `/unapprove` | 기관 담당자 | 문장이 하나도 없으면 승인 409 |
| `POST /recipients/{id}/visits/start` · `/end` | 배정된 요양보호사 | 시작: 열린 방문이 있으면 409 / 종료: 이 수급자의 내 열린 방문이 없으면 409 |
| `GET /recipients/{id}/visits` | 직원 | 최근 7일 방문 시각 |
| `POST /org/alerts/{id}/resolve` | 기관 담당자 | `guardian_message` 추가(선택). 있으면 보호자 공유 |
| `GET/POST /recipients/{id}/messages` | 직원 | 최근 50개 / 1~500자 |
| `GET /guardian/home` | 보호자 | 방문마다 `summary`(승인된 것, 범위로 거른 문장), `visits`(방문 시각), `notices`(공유된 처리 결과) 추가 |

## 5. 화면

- **기록 화면(기관 담당자)**: "보호자 하루 요약" 카드 — 만들기, 문장별 수정·삭제, 근거 분류 배지, 승인/승인 취소. 요양보호사는 읽기만.
- **수급자 화면(요양보호사)**: 상단에 "방문 시작" / "방문 중 · 14:02부터 · 방문 종료". 업무 메시지 섹션(직원 모두).
- **센터 인박스**: 처리 폼에 "보호자에게 보낼 안내 (선택)".
- **보호자 화면**: 맨 위 오늘 방문 시각, 센터 안내, 방문별로 승인된 요약을 먼저 보여 주고 세부 항목은 "자세히"로.

## 6. 테스트

- 요약: 만들기 → 승인 전 보호자에게 안 보임 → 승인 후 보임, 범위 밖 근거 문장 빠짐(보호자 둘로 확인), 수정 문장 반영·근거 유지·문장 추가 불가, 승인된 요약 다시 만들기 409, 공유 동의 없으면 409, 한도 합산.
- 방문: 시작/종료, 중복 시작 409, 다른 사람 종료 불가, 보호자 화면 표시.
- 처리 결과 공유: 안내문만 가고 근거·우려 원문은 보호자 응답에 없음.
- 메시지: 직원만, 배정 해제 시 차단(접근 표).
- 접근 표에 새 API 추가, 실제 모델 테스트에 보호자 요약 추가.
- E2E: 기관 담당자 요약 승인 → 보호자 화면, 방문 시작/종료, 처리 결과 안내.
