# 4단계 설계: 변화 알림 · 긴급 우려 · 센터 인박스 · 기분·식사량 추이

작성일 2026-11-27

## 1. 목표와 범위

기획안의 "변화 알림" 항목을 동작하게 만든다.

> 7일 이내 서로 다른 두 방문의 확정 기록에 같은 부위의 불편이 있거나, 비교 가능한 두 방문에서 식사량이 줄면 기관에 근거와 함께 알림. 미확인 항목 제외, 같은 사유의 미처리 알림 통합, 정정 시 재평가. 담당자가 조치 결과 기록. 긴급 상황은 기존 연락 절차 적용.

포함
- **구조화된 상태 값**: AI 분류가 항목마다 불편 부위(`body_part`)를, 방문마다 식사량(`meal_level`)과 기분(`mood`)을 근거와 함께 제안한다. 요양보호사가 검토 화면에서 확인·수정한 값만 저장한다.
- **변화 알림 규칙** 두 가지(같은 부위 불편 반복, 식사량 감소). 확정할 때 서버가 규칙을 평가하고, 근거 항목을 단 알림을 만든다. 같은 사유의 미처리 알림이 있으면 새로 만들지 않고 근거를 합친다.
- **긴급 우려 수동 제출**: 요양보호사가 규칙과 관계없이 우려를 직접 올린다.
- **센터 인박스**: 기관 담당자가 미처리 알림을 보고 조치 결과(조치함 / 오탐)와 메모를 남긴다.
- **방문 전 확인 화면**에 미처리 알림, **기분·식사량 추이**(최근 30일).

제외
- 정정(확정 기록 수정)은 6단계. 이번 단계에서는 규칙 평가를 함수 하나(`evaluate_alerts`)로 두고 확정 때 부른다. 6단계에서 정정 뒤에도 같은 함수를 부른다.
- 알림을 보호자에게 공유 → 5단계
- 푸시·문자 알림 (앱 안 인박스만). 긴급 상황은 앱이 아니라 기존 연락 절차(119, 센터 전화)를 따른다고 화면에 적는다.

## 2. 결정과 이유

| 결정 | 이유 |
|---|---|
| 규칙은 **확정된 구조화 값**으로 평가 | 자유 문장에서 키워드로 "무릎"을 찾으면 "무릎 담요를 덮어 드림" 같은 오탐이 많다. AI가 부위·식사량을 제안하고 사람이 확정한 값만 쓰면 규칙은 단순한 비교가 되고, 근거도 항목으로 바로 연결된다. |
| AI가 알림 여부를 판단하지 않음 | 기획안 원칙(위험 판단·조언 안 함)과 같다. AI는 값을 뽑기만 하고, 알림은 서버 규칙이 만든다. 규칙은 테스트로 고정할 수 있다. |
| 불편 부위는 **좌우 구분 없는 12개 값** | 좌우를 나누면 "오른쪽 무릎"과 "무릎"이 다른 부위가 되어 놓친다. 알림은 확인을 요청하는 것이라 놓치는 쪽보다 한 번 더 보는 쪽이 낫다. |
| 식사량은 **0~4 다섯 단계**, **2단계 이상 줄면** 알림 | "거의 못 드심/조금/절반/대부분/다 드심" 정도가 말로 남기는 기록에서 구분 가능한 수준이다. 한 단계 차이(절반 → 조금)는 그날 메뉴로도 흔해서 오탐이 많다. 기준값은 설정으로 둔다. |
| "비교 가능한 두 방문" = **둘 다 식사량이 기록되고 7일 이내** | 식사 언급이 없는 방문을 0으로 보면 안 된다. |
| "미확인 항목 제외" = 확정 전 기록과 **발화자 미확인 항목** 제외 | 발화자가 불분명한 말로 알림을 만들지 않는다. |
| 같은 사유 통합은 **부분 unique 인덱스** `(recipient_id, kind, key) WHERE status = 'open'` | 같은 수급자·같은 부위의 미처리 알림은 하나만. 근거만 추가된다. 처리된 뒤 다시 생기면 새 알림. |
| 확정과 같은 트랜잭션에서 평가 | 워커 큐를 하나 더 두지 않는다. 규칙 두 개가 최근 7일 기록 몇 건만 읽어서 빠르다. |
| 긴급 우려는 **알림과 같은 테이블**(kind=`urgent`) | 인박스에서 한 목록으로 보고 같은 방식으로 처리한다. 통합하지 않도록 key는 매번 새 값. |

## 4. AI

- `DraftItem.body_part`: 그 항목이 특정 부위의 불편·통증을 말할 때만. 아니면 null.
- `Classification.state`: `{meal_level, meal_evidence, mood, mood_evidence}`. 언급이 없으면 null.
- 프롬프트 규칙 추가: 부위·식사량·기분은 전사문에 근거가 있을 때만, 근거 구절을 그대로 옮긴다. 판단·조언하지 않는다.
- 후처리: 근거 구절이 전사문에 없으면 그 값은 버린다(null). 항목의 body_part는 항목 근거를 따른다.
- draft JSON에 `state: {meal_level, meal_evidence, mood, mood_evidence, ...locate}` 추가. 1~3단계 초안에는 없다(화면은 빈 값으로 처리).

## 5. 규칙 (`app/alerts.py`)

`evaluate_alerts(db, record)`: 확정된 기록 하나를 기준으로 평가한다.

1. **repeated_discomfort**: 이 기록의 항목 중 `body_part`가 있고 `speaker_uncertain = false`인 것마다, 같은 수급자의 다른 확정 기록 중 방문일 차이 7일 이내이고 같은 부위 항목이 있는 기록을 찾는다. 있으면 key=부위로 알림을 만들거나(없으면) 근거를 합친다(있으면).
2. **meal_drop**: 이 기록에 식사량이 있으면, 방문일 기준 바로 앞과 바로 뒤의 식사량이 있는 확정 기록(7일 이내) 중 앞 기록보다 뒤 기록이 `MEAL_DROP_LEVELS`(2) 이상 낮은 쌍이 있으면 key=`meal`로 알림.
- 근거는 `(record_id, item_id)` 기준으로 중복 없이 합친다. 식사량 근거는 item_id 없이 기록과 "식사량: 절반 → 조금"처럼 쓴다.

## 6. API

- `POST /records/{id}/confirm` 확장: 항목에 `body_part`, 본문에 `meal_level`, `mood`. 확정 후 `evaluate_alerts`. 응답에 `meal_level`, `mood`, 항목 `body_part`.
- `POST /recipients/{id}/concerns` (배정된 요양보호사): `{note}` 1~500자 → 긴급 우려 알림. 건강정보 동의 필요.
- `GET /recipients/{id}/alerts` (직원): 이 수급자의 미처리 알림.
- `GET /recipients/{id}/trends?days=30` (직원): `[{record_id, visited_on, meal_level, mood}]` 확정 기록, 방문일 오름차순.
- `GET /org/alerts?status=open|resolved` (기관 담당자): 센터 알림 목록(수급자 이름 포함), 미처리는 오래된 순, 처리됨은 최근 순 50개.
- `POST /org/alerts/{id}/resolve` (기관 담당자): `{resolution, note?}`. 이미 처리됐으면 409.
- 접근 표에 모두 추가한다.

## 7. 화면

- **검토**: 항목 수정 폼에 "불편 부위" 선택, 카드에 부위 배지. 항목 목록 위에 "오늘 상태" 카드: 식사량·기분 선택(AI 제안이면 "AI 제안" 표시와 근거 구절). AI가 값을 제안했으면 확인 버튼을 눌러야 확정 가능(다른 AI 항목과 같은 규칙).
- **확정 화면**: 오늘 상태와 부위 배지.
- **방문 전 확인**: 맨 위에 미처리 알림(근거 날짜 링크), 기분·식사량 추이(최근 30일, 방문일별 막대 + 기분 표시), 요양보호사에게 "긴급 우려 올리기" (안내: 응급 상황은 119와 센터 전화가 먼저).
- **센터 관리**: "알림" 섹션 — 미처리 목록, 조치함/오탐 + 메모로 처리, 최근 처리 목록. 홈의 센터 관리 링크에 미처리 알림 수.

## 8. 테스트

- 규칙 단위: 같은 부위 7일 이내 두 방문 → 알림 / 8일 → 없음 / 같은 방문 안 두 항목 → 없음 / 발화자 미확인 → 없음 / 미처리 알림 있으면 근거만 합침 / 처리 후 다시 생기면 새 알림 / 식사 4→2 알림, 3→2 없음, 식사 기록 없는 방문은 비교하지 않음, 늦게 확정된 앞 방문으로도 평가.
- 후처리: 근거 없는 상태 값 버림, 잘못된 부위 값 거부.
- API: 확정 → 알림 생성 흐름, 긴급 우려, 인박스 처리(409 두 번), 추이.
- 접근 표 갱신, 실제 모델 테스트에 부위·식사량 확인 추가.
- E2E: 같은 부위 불편 두 번 기록 → 방문 전 확인에 알림 → 기관 담당자 인박스에서 처리, 긴급 우려 올리기.
